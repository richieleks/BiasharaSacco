# Biashara SACCO Management System

## Overview
This project is a comprehensive SACCO (Savings and Credit Cooperative Organization) management system designed to streamline operations for cooperative banking. It enables the management of members, savings accounts, loans, and financial transactions. The system aims to provide a robust, user-friendly platform for SACCOs to manage their core business processes efficiently, improving member services and financial oversight.

## User Preferences
Preferred communication style: Simple, everyday language.

## System Architecture

### UI/UX Decisions
The frontend utilizes React 18 with TypeScript, built on Radix UI components and the shadcn/ui design system for a modern, accessible, and consistent user experience. Styling is managed with Tailwind CSS, incorporating custom CSS variables for flexible theming. The design emphasizes responsiveness, catering to both desktop and mobile users, and incorporates a custom SACCO-themed color palette. Key UI components include interactive analytics charts (Recharts), dynamic tables with server-side pagination, and intuitive forms for various operations. Server-side pagination is implemented across all major list pages (Members, Transactions, Loans, Savings, Audit Logs) using the `useServerPagination` hook (`client/src/hooks/useServerPagination.ts`) which manages page/limit/search state and builds query params. The paginated API response format is `{ data: T[], total: number }`. Search inputs use a 400ms debounce. The `Pagination` component (`client/src/components/ui/pagination.tsx`) supports items-per-page selection (10/25/50/100) and shows "All" only when total items <= 100. Backend paginated storage methods use SQL `LIMIT`/`OFFSET` with `ilike` for search and `count()` for totals. Loan summary stats (active count, outstanding amount, default rate) are computed via a dedicated `GET /api/loans/stats` endpoint using SQL aggregation over the full dataset, not from the paginated slice. Audit logs page supports resource and action dropdown filters alongside the search input, passed as query params to the backend. Profile and settings functionalities are implemented as standalone pages for enhanced user experience, complemented by a collapsible sidebar for improved navigation.

### Technical Implementations
The system is divided into a `client/` (React frontend) and `server/` (Express.js backend) architecture, with `shared/` for common TypeScript types and database schema.
- **Frontend**: Wouter for routing, TanStack Query for server state management, and Vite for building.
- **Backend**: Node.js with Express.js, TypeScript, and ES modules. Drizzle ORM is used for type-safe database operations with PostgreSQL (Neon serverless). Authentication is handled via local username/password authentication with bcrypt for password hashing, and sessions are managed using Express sessions with PostgreSQL storage.
- **Authentication**: Fully DB-driven RBAC with roles (admin, treasurer, committee, teller, member) and permissions stored in `roles`, `permissions`, and `role_permissions` tables. On startup, `seedRBAC()` in `server/seed.ts` idempotently ensures all system roles, permissions, and role-permission mappings exist — it checks each role/permission individually and only inserts missing entries, making it safe to run repeatedly. The backend middleware (`server/rbac-middleware.ts`) checks permissions from the DB for each request. The frontend fetches user permissions via `/api/auth/permissions` and uses them in the `useRBAC` hook (`client/src/hooks/useRBAC.ts`) for menu-level navigation filtering and access control — each menu item in `ALL_NAVIGATION_ITEMS` (`client/src/lib/rbac.ts`) requires a specific `{action, resource}` permission, and the sidebar only renders items the user's role grants. Admin role bypasses all permission checks. Permission management UI is in `client/src/components/rbac-management.tsx`, accessible from the RBAC tab in admin settings.
- **Financial Operations**: Includes comprehensive management of savings accounts, loans (with a multi-approver committee workflow: Member Application → Committee Evaluation with configurable minimum approvers → Treasurer Disbursement, dynamic repayment calculations, and conditional guarantor workflows), and transactions. Only users with the `committee` role can approve loans at the committee stage (admin cannot). The `minLoanApprovers` system setting controls how many committee members must approve before a loan moves to disbursement (default: 2). Individual approvals are tracked in the `loan_approvals` table. An advanced interest calculation system supports various methods (simple, compound, reducing balance) and manages financial years. Share capital calculations use the system-wide share price from Membership Configuration (admin settings), not per-member `shareContribution` field. The `shareContribution` field in the members table is a legacy per-member value; all share capital expected amounts are calculated as `systemSharePrice × numberOfShares`.
- **Guarantor Requests**: Members can view and respond to guarantor requests at `/guarantor-requests` (standalone page: `client/src/pages/guarantor-requests.tsx`). Notifications with `actionUrl: '/guarantor-requests'` link directly to this page. The page uses `/api/guarantors/pending` (auto-resolves logged-in user's member ID). Members see a "Guarantor Requests" nav item via `personal-guarantors` permission. The page is accessible to all authenticated users so that notification links work regardless of role.
- **Currency Formatting**: All monetary amounts use `formatCurrency(amount, prefix="UGX")` from `client/src/lib/utils.ts` with 0 decimal precision. Never use inline `UGX ${...toLocaleString()}` patterns. Keep `.toFixed(2)` only for data storage/API calls, not display.
- **Business Logic**: A robust business rules validation system ensures compliance with SACCO regulations, providing real-time eligibility checks for loan applications based on membership duration, active saver status, and savings-to-loan ratios.
- **Notifications**: A real-time notification system with WebSocket support keeps users informed of critical activities, offering various notification types and priority levels.
- **User Preferences**: Per-user settings (theme, language, notification toggles, auto-logout timer) are persisted in the `user_settings` table as a JSON blob per user. The `GET /api/auth/settings` endpoint returns saved settings merged with defaults, and `PATCH /api/auth/settings` upserts them. The admin-settings Preferences tab loads saved values on mount via react-query and resets the form.
- **Dark Mode**: Full dark mode support via `useTheme` hook (`client/src/hooks/useTheme.ts`) which reads theme preference from user settings and applies the `dark` CSS class to `<html>`. Tailwind's `darkMode: ["class"]` is configured, and CSS variables in `.dark` class (in `index.css`) swap all theme colors. All pages, components, and dynamic class strings include `dark:` variants for text, backgrounds, borders, hover states, and accent colors. Custom CSS classes (`metric-card`, `section-card`, `sacco-gradient-subtle`, `page-skeleton`) also include dark mode overrides.
- **SACCO Operational Accounts**: Chart of Accounts system with 5 account types (asset, liability, equity, revenue, expense). 27 default accounts are seeded on startup via `storage.seedDefaultSaccoAccounts()` in `server/index.ts`. Double-entry journal entries use database transactions for atomicity (`db.transaction()` in storage methods). Frontend page at `/sacco-accounts` with four tabs: Chart of Accounts (grouped by type), Journal Entries (paginated with reversal support), Mappings (fee/rate to GL account mappings), and Summary (balance sheet check). The `sacco_account_mappings` table maps each fee/rate type to its corresponding debit and credit GL accounts. 14 default mappings are seeded via `storage.seedDefaultAccountMappings()`. **Automatic journal entries** are created by the `recordJournalEntry()` helper in `server/routes.ts` which looks up the mapping by key, validates the amount, and creates a double-entry journal entry. It's wired into: savings deposits (`member_deposit`), withdrawal approvals (`member_withdrawal`), loan disbursements (`loan_disbursement`), loan repayments (`loan_repayment_principal`), loan top-up settlements (`loan_repayment_principal`), loan acceptance/processing fees (`loan_processing_fee`), and share capital payments (`share_capital_contribution`). Errors in journal entry creation are caught and logged but don't block the primary financial operation. RBAC permissions: `read:sacco-accounts` and `update:sacco-accounts` granted to admin, treasurer, committee (read+update), and teller (read only).
- **Data Management**: Features include Excel file upload for bank statement processing and transaction import, comprehensive account statement generation, and an audit logging system for tracking all critical system activities. Loan import requires selecting a loan type beforehand and only maps to existing members (no auto-creation of members or savings accounts).
- **Bank Transfer Schedules**: KCB-format Excel file generation for monthly salary deductions. Two schedule types: (1) Savings deduction schedule — pulls active members with `monthlySavings > 0` and a bank `accountNumber`, (2) Loan repayment schedule — pulls active/disbursed loans with `monthlyPayment > 0`. Generated via `GET /api/reports/savings-schedule?month=Mar` and `GET /api/reports/loan-schedule?month=Mar`. Files follow KCB bank transfer format with columns: P, SRC_BRANCH, DR_ACC, AC_NAME, CURR, AMOUNT, DEST_BRANCH, CR_AC_NO, AC_NAME, CR_CURR, DETAILS_OF_PYT, PAYMENT_TYPE, SWIFT_CODE, and ordering customer details. SACCO bank details (branch code, account number, SWIFT code, address, etc.) are configurable in Admin Settings under "SACCO Bank Details" card in the Business Rules tab. Cell values are sanitized against Excel formula injection. The "Bank Schedules" tab on the Reports page (`client/src/pages/reports.tsx`) provides month selectors and download buttons for both schedule types.
- **Member Activity Tracking**: Automatic tracking of member savings activity via `lastSavingsDate` field on the members table. Updated on every savings deposit (individual and bulk import). A background activity checker runs on startup and daily (24h interval), scanning all active/inactive/dormant members: 3+ months without savings and no running loans → status set to `inactive`; 6+ months → `dormant`. Members who save again are automatically reactivated. Manual trigger available via `POST /api/members/check-activity`. Activity report at `GET /api/reports/member-activity` returns summary counts (active, inactive, dormant, at-risk) plus detailed member lists. Reports accessible in the "Member Activity" tab on the Reports page (`client/src/pages/reports.tsx`), showing clickable summary cards, filterable tables (dormant/inactive/at-risk), days since last saving, and a "Run Activity Check" button. The `dormant` status was added to the member status enum.
- **Member Exit Workflow**: Member exits go through a two-step treasurer approval process. Staff submit an exit request via the "Process Exit" button on member-details (POST `/api/members/:id/exit`), which creates a `member_exit_requests` record with `pending_treasurer` status instead of immediately closing the account. Eligibility logic: active loans are a blocker only if savings are insufficient to cover outstanding balance; if savings >= outstanding loan, `canUseSavingsForLoan: true` is set (not a blocker — treasurer settles it upon approval). Guarantor obligations on active loans remain a hard blocker. The Treasurer reviews requests at `/exit-requests` (page: `client/src/pages/exit-requests.tsx`, requires `approve:members` permission), where they can approve (triggering loan settlement from savings, exit fee charge, and member status update to "exited") or reject with a reason. The `member_exit_requests` table tracks all history including approval/rejection metadata.

### Feature Specifications
- **User-Member Auto-Sync**: The `users` and `members` tables are kept separate but tightly synchronized via the `ensureMemberProfile()` helper in `server/routes.ts`. Whenever a user is created, updated, or logs in, a member profile is automatically created if one doesn't exist. Name and email changes on either side are synced to the other. Every user always has a corresponding member profile with a savings account.
- **User Management**: Creation, profile management, and role assignment for SACCO members and staff. User Management and RBAC Management are combined into a single "Users & Roles" tab in admin settings.
- **Savings Accounts**: Creation, management, deposits, withdrawals, and detailed statement generation. Members can self-service request withdrawals from their own accounts via the "Request Withdrawal" button on the savings page (`MemberWithdrawalForm` component). The backend `POST /api/savings/withdraw` enforces ownership — non-staff users can only withdraw from accounts belonging to their member profile (IDOR protection). Withdrawal approvals (`PATCH /api/transactions/:id/approve` for withdrawal type) are restricted to treasurer and admin roles only — the backend returns 403 for other roles, and the frontend hides the Approve button for non-treasurer/admin users. The `/savings` route is accessible to all authenticated users; the page auto-detects member vs staff and shows either personal view or admin view accordingly. "My Savings" nav item is available for members via `personal-savings` permission.
- **Loans**: Application, multi-stage approval, guarantor management, dynamic repayment schedules, business rule validation, and loan top-up module (members can request additional funds on active loans, consolidating outstanding balance with new amount into a single replacement loan through the standard approval workflow). Top-ups follow the same guarantor workflow as new applications: if the loan type requires guarantors AND the member's savings don't fully cover the total new principal, the form transitions to a guarantor management step after submission.
- **Transactions**: Comprehensive tracking, auditing, and reporting.
- **Reporting & Analytics**: Dashboards with KPIs, transaction history, member activity, and financial summaries, including visual analytics charts.
- **System Settings**: Differentiated user and admin settings, allowing for personal preferences and system-wide configurations (e.g., loan limits, security policies, email setup, business rules).

- **Security Features**:
  - **Session Timeout**: `isAuthenticated` middleware in `server/replitAuth.ts` tracks `lastActivity` timestamp on each request and destroys sessions exceeding the configured `sessionTimeout` minutes (admin settings). Inactivity-based expiry.
  - **Password Complexity**: `validatePasswordComplexity()` in `server/localAuth.ts` enforces rules based on `passwordComplexity` setting. Low: 6+ chars. Medium: 8+ chars with uppercase, lowercase, number. High: 12+ chars with uppercase, lowercase, number, special char. Enforced on user creation (`/api/auth/create-user`) and password change (`/api/auth/change-password`). `GET /api/auth/password-requirements` returns current level and description.
  - **Login Lockout**: Users table has `failedLoginAttempts` (integer) and `lockedUntil` (timestamp) columns. On failed login, attempts increment; when reaching `maxLoginAttempts` setting, account locks for 30 minutes. Successful login resets counters. Admins can unlock via `POST /api/auth/users/:id/unlock`. Frontend shows "Locked" badge and unlock button in Users list.
  - **Two-Factor Authentication (TOTP)**: Uses `otpauth` library. Users table has `twoFactorSecret` and `twoFactorEnabled` columns. Setup via `POST /api/auth/2fa/setup` (generates secret + TOTP URI), verify via `POST /api/auth/2fa/verify`, disable via `POST /api/auth/2fa/disable`. Login flow: when 2FA is enabled, initial login returns `requiresTwoFactor: true` without creating a session; frontend shows TOTP input dialog; `POST /api/auth/login/2fa` validates the TOTP code and completes authentication. Profile page (`client/src/pages/profile.tsx`) has `TwoFactorSetup` component with QR code display, secret key copy, and enable/disable controls.
- **Database Backup System**: `server/backup.ts` exports all major tables (members, savings, loans, transactions, system settings) to JSON files in `backups/` directory. `POST /api/admin/backup` triggers manual backup. `GET /api/admin/backups` lists available backups. `GET /api/admin/backups/:filename` downloads a backup file. Scheduled backups run via `setInterval` based on `backupFrequency` setting (daily/weekly/monthly), controlled by `autoBackupEnabled`. Schedule restarts when backup settings change. Keeps max 10 backup files with automatic cleanup. Frontend: `BackupManagementCard` component in admin settings shows backup history with download buttons and manual trigger.
